ThoxOS Rust Foundation: Protection POC, Virtual Lab, and Directional Stack

A local-first engineering draft toward Rust firmware, kernel, and OS surfaces for ThoxKey, ThoxAir, ThoxMini, ThoxClip, and host platforms.

Status box (2026-11-11, America/Chicago): Public technical draft for founder review. Not peer reviewed. Not submitted to arXiv. Catalog entry prepared as draft-only (no live site publish without Tommy/Craig). Authors: Craig Ross (CEO), Tommy Xaypanya (CTO), THOX.ai LLC. AI assistance disclosed. Founder gate required before publish.

Abstract

THOX is assembling a Rust-first path from device provisioning to kernel and host OS surfaces while keeping MeshStack and ThoxKey firmware proprietary. This paper records a recreateable protection and provisioning POC (THOX Guard), a QEMU virtual lab with hashed evidence and captures, a license-aware candidate map (phil-opp blog_os, Redox OS, and the rust-os-comparison catalog), and a directional stack that separates ThoxInux (Ginux Apache-2.0 Linux-ABI track), linux-thox packaging, and clean-room kernel-lab specifications. Observed results in this revision include software integrity provision/verify/attest across host and Alpine guests, a directional freestanding kernel boot under QEMU with a stable loaded-image SHA-256, and recreateable lab markers. Hardware root-of-trust, bare-metal device qualification, and a product kernel on THOX devices are explicitly not claimed.

1. Introduction

ThoxOS today spans desktop application surfaces and multiple engineering OS tracks. The Kickstarter device family (ThoxKey, ThoxAir, ThoxMini, ThoxClip) needs a coherent provisionable protection layer and an honest research path toward a true Rust firmware/kernel/OS without relabeling unfinished work as shipped product.

3. System / method

3.1 Directional stack

Layers L0–L7 map firmware → boot → kernel tracks → protection → provisioning → AI runtime → cloud/container lab. See docs/stack/CURRENT_STACK.md in the program hub.

3.2 Protection POC (THOX Guard)

Canonical POC name: THOX Guard (draft PR #26, branch cursor/poc-thox-guard-cebf). Linux userspace agent with TOML policy, BLAKE3 and SHA-256 baselines, THOX ed25519 signatures, minisign 0.11 prehashed signatures, and a hash-chained log. Installer profiles: thoxkey-host, thoxair, thoxmini, thoxclip, desktop-linux, server, cloud-vm, container. Complementary hub branch cursor/thoxos-rust-foundation-87e7 retains an earlier thox-protect CLI and stack/paper orchestration docs.

3.3 Directional kernel track

Freestanding x86_64 research kernel adapted from blog_os post-04 patterns with bootloader 0.9.x, QEMU BIOS boot, serial banner, and a SHA-256 of loaded PT_LOAD bytes. Status: directional research, not a product kernel and not a boot on ThoxAir/Mini/Clip/Key hardware.

3.4 Virtual lab

Primary recreate path: bash lab/run.sh on the Guard branch (tests, clippy, cross builds, host scenario, installer, kernel image, QEMU x86_64, Alpine aarch64/armv7 guests, container). Compare with lab/VALIDATE.md. Evidence pack: lab/evidence/2026-11-11/. Foundation branch also records vlab/scripts/run_lab.sh and Alpine cloud-vm probes under vlab/evidence/.

7. Limitations

  • Attestation and baselines are software-only; not TPM/TEE-backed. Root can still replace agent and baseline together.
  • Enforcement hooks exist but are compiled out (poc-enforcement-exec off).
  • macOS and Windows are not implemented.
  • No physical device flashing or field qualification in this revision.
  • Directional kernel is QEMU x86_64 only; not a THOX device boot.
  • raspi1ap Pi Zero-class machine boot remains unproven (issue #27).
  • Catalog publication, Zenodo DOI, and arXiv submission are not established.

8. Conclusion

The program hub and Guard POC deliver a ready-to-run protection/provisioning package, recreateable lab evidence with captures and hashes, a license-aware directional stack, and this standalone HTML draft for the research catalog — pending founder publish approval.
